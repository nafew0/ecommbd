# Changelog

All notable changes to Ecomm BD. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed

- **WooCommerce import:**
  - A store whose order-number plugin had reached 1,000,000 or more stopped at the very end with ORDER_NUMBER_RANGE_REQUIRES_REVIEW (a real store: 1,001,102). New order numbers now jump past the highest WooCommerce number in one step; only a jump of over a billion (a typo or a date-based number) asks for review.
  - Emoji in product descriptions came out blank and counted as failed images: WordPress stores them as small images from its own server (s.w.org). They now become emoji characters again.
  - Imported orders were hard to find: they are kept as read-only history, apart from live orders, and only the migration page and each customer's page showed them. They now have their own page, **Orders → WooCommerce orders** (search by number, phone or name), and the Orders page says where they are. Customers' order counts, delivered count, total spent and last order now include their WooCommerce orders (recounted after each import).
  - The migration page is now five clear steps (Connect → Check → Import → Old links → Go live), one at a time, opening on the step the store has reached. Connecting offers the three ways side by side (WordPress plugin, export file, API key), each with numbered instructions. The newest connected store is selected on its own, a finished check no longer jumps away before its results are seen, and the resume button only shows for a run that stopped on an error.
  - An import stopped by a restart or deploy stayed "running" with no progress until someone clicked resume. A check every five minutes now puts it back to work from where it stopped, once its five-minute lock has run out (so within about 10 minutes).
- The merchant admin no longer shows "Unexpected Application Error! Failed to fetch dynamically imported module" when a tab that was open during a deploy opens another screen: it reloads itself once to get the new version. If the screen still can't load, it shows a short message with a Reload button (Bangla and English) instead of the developer error page.
- **Phase 18 review (online payments):**
  - Cancelling an order that is waiting for its online payment cancels that payment, whoever cancels it. Money that arrives later is held in Payment reviews ("paid after the order was cancelled"), never settled on a cancelled order; the review screen offers only refund or resolve for it.
  - Payments whose outcome was unclear (a bKash Execute that timed out) are checked again for up to a week, so a late success still pays the order.
  - The pay link starts the gateway once, even when the page refresh and the button arrive together or the shopper reloads; bKash no longer rejects the callback.
  - A refund whose answer was lost shows as "Refund processing" and is checked with the gateway, never as refused. SSLCommerz refund requests are never retried, and bKash never sends a second refund while one is in progress. Refund refusals and Test connection results are in Bangla and English.
- **Phase 19 review (couriers):**
  - A booking with no clear answer (timeout, dropped connection, 5xx, 429) stays live and is checked with the courier before booking again: never booked twice. Pathao has no lookup, so staff check its panel.
  - "Booked by hand" accepts any courier name, including Bangla (it crashed past 16 characters).
  - Steadfast "pending" no longer marks orders shipped; "cancelled" before the parcel leaves cancels the booking instead of returning the order.
  - Bulk booking shows why each order wasn't booked; staff are warned when the cash to collect changes after booking; "waiting for <courier>" during outages; Pathao places reset when the mode changes; webhook secrets are made only from settings; order moves that fail are retried.
- **Phase 20 review (Meta Pixel and Conversions API):**
  - No secret addresses (tracking and payment links, order codes) go to Meta or the event log, and private pages aren't tracked. Shopper IP and browser are cleared from all orders after 90 days, placed or not.
  - A refused token or Pixel holds that Pixel's events with a warning until a new token is saved (it used to fail every event, one request each). Purchase is sent before browser events, the queue is bounded, and sending runs can't overlap.
  - Sales pages send ViewContent and Purchase; AddToCart fires only when the add worked, InitiateCheckout once per cart. The Meta script loads only on stores with a Pixel. "Send test event" needs a test code. The event log has paging and an order filter.
- `packages/shared` meets its 100% coverage gate again (`npm test` failed on the M4 files).

- The merchant admin's product, category and stock lists showed broken thumbnails (in development too): those lists returned an image's stored path (`preview/a3/photo.jpg`) instead of its address. They now get the full address the way Vendure gives its own images (`ASSET_URL_PREFIX` on live stores).
- **Phases 21–22 review (WooCommerce migration):**
  - **Bangla addresses stay the same.** WordPress sends Bangla slugs percent-encoded; they were saved as `e0a6b2…`. They're now decoded, so `/product/লাল-শার্ট/` keeps its address, and old links point at it.
  - **Stores whose links have no trailing slash import.** `/product/shirt` and `/product/shirt/` no longer count as a redirect loop that failed the import.
  - **The store's own pages always win over old links.** The storefront looks a redirect up only when it has no page for the address (WordPress's `/?p=123` links are looked up first), so an old WordPress page can't send `/privacy-policy/` to the home page. Old pages now go to our page with the same address, if there is one. Rules can't claim the home page, the sitemap, robots.txt or our private paths.
  - **Staff rules survive imports, and can be deleted.** Rules saved on the cutover screen are marked as staff rules; a catch-up sync no longer overwrites them. A rule saved for one of our live pages no longer re-points other old links.
  - **One bad record no longer stops an import for good.** A record whose variations, notes or refunds can't be read is skipped with an issue, after checking that the old host is still answering (if it isn't, the run stops at that record, to resume later). A missing parent category leaves the category at the top level with an issue, instead of failing every resume. A variation with no price is left out with a warning.
  - **Order numbers continue after the last WooCommerce number** on a fresh store too; the first real order used to repeat it.
  - **The "importing" mark reaches every listener.** It was lost when Vendure copied the request for event listeners, so caches were purged during imports and a future Meta listener would have fired.
  - **Password hashes don't linger.** Revoking or replacing a helper pairing deletes its upload at once, and after an import the customers' WordPress hashes are dropped from the uploaded data (they are kept only encrypted, per customer). The daily cleanup also removes revoked and never-used pairings. Imported hashes with extreme work factors are refused (they'd cost seconds per login attempt).
  - **The upload endpoint checks the signature before taking any lock**, so unsigned requests can't hold up a real upload.
  - **The WordPress helper plugin is rewritten to WordPress coding standards** (`apps/wp-migrator`): small classes with comments instead of one file of very long lines, WordPress's own translation functions with Bangla shipped in the plugin, PHP 7.4 compatible. It is much faster on cheap hosting: one run keeps sending within a budget taken from the host's own time and memory limits (it used to send 50 records per run, shrinking to 1), the chunk size grows back after fast chunks, and "Continue now" runs the same loop. It shows the destination store's address and asks the merchant to confirm it before sending anything, never exports courier keys from shipping settings or secret-looking order data, and uses an atomic lock. `apps/wp-migrator/tests/run.sh` checks it on PHP 7.4 / WordPress 5.8 / WooCommerce 4.9 and on the latest versions with both kinds of order storage.
  - **Used coupons import** with the uses they have left (used up: imported disabled). Empty SEO fields no longer wipe SEO written here. Order notes are read in one request (orders with 100+ notes looped). Page sizes grow back after the old host recovers. The dry run gives an estimated import time in seconds, from its own reading time, the record counts and the images. Runs record who started them. The missing-pages list ignores bot probes (`/wp-login.php`), no longer misses paths such as `/t-shirts/`, and makes room for new ones when full. A redirect lookup that fails keeps the page instead of showing "unavailable".
- Phase 04 review: confirm, pack and cancel permissions now apply to Vendure's standard order mutations as well as the merchant admin. Native cancellation checks the reason, required note and settled payments before changing lines, under a transaction and order lock. Direct cancellation transitions cannot leave live quantities and reserved stock behind.
- The home widget is labelled **Order value today** in English and Bangla, with its meaning explained. The Admin API exposes `todayOrderValue`; `todaySales` remains a deprecated alias with the same permission check.
- Status-only returns now require confirmation and explain that returned quantities, stock and payments are unchanged. Returned/cancelled order pages no longer show a delivery collection instruction. The stock, partial-return, refund and courier-payment contract is recorded in `docs/decisions/order-states.md` for the next implementation work.
- Phase 16 review: sales page prices (packs and the add-on) now apply only to an order made with the page's own order form. A normal cart never gets them, whatever attribution cookie the browser sends, and the add-on's special price needs the page's product in the same order. Ad shoppers who buy a pack's quantity in the normal cart no longer get a "the total has changed" refusal on the first tap. Placed orders from before keep their offer if staff edit them (migration `sales-page-offer`).
- A sales page whose address is taken at the full 80 characters (a long Bangla title) no longer fails with a server error: the merchant is told and offered a free address. Addresses cut at the limit no longer end with a hyphen.
- Price fields in the sales page settings (packs, add-on) and in the page editor read "990.00" as ৳990 (it became ৳99,000) and take Bangla digits; "990.50" is refused with a message in Bangla and English, since prices are whole taka.
- The Bangla "not enough in stock" label on sales pages said "out of stock".
- Phase 14 review: the thank-you page shows "track your order" for an order this browser can't see (a mistyped code, or after the 2 hours a guest can read it) instead of the error page.
- When stock runs short during checkout (3 in the cart, 2 left), the cart is lowered to what's left and the shopper is told which item changed and to what quantity, in Bangla and English, instead of failing every time.
- An order is never left stuck waiting for payment: any failure while paying (an error, a timeout) moves it back to the cart, so the shopper can try again or change it.
- If the core placed an order but its answer never reached the storefront (a timeout), the retry or the checkout page shows that order's thank-you page instead of an empty cart that invites a second order. With JavaScript, an error page no longer replaces the checkout form, so a retry keeps the shopper's details and the same idempotency key. The back button or a second tab now says "Your order is already placed."
- Docs: the checkout's one-order-per-tap decision and the storefront's scripts (plain scripts, no Preact) in `architecture.md` now say what the code does; the attribution script on every page (about 1 KB) is recorded as a deliberate exception to zero JavaScript. A Playwright test now opens the tracking link `/t/<token>/`.

### Added

- **WooCommerce migration by export file** (WordPress helper 0.3.0): for old sites that can't reach Ecomm BD, **Create export file** in WooCommerce → Move to Ecomm BD writes the store to a `.jsonl.gz` file in the background, and **Download export file** saves it. In the Ecomm BD admin, **Or import an export file** on the migration page reads it; then dry run and import as after an upload. The file holds the same chunks as the upload and passes the same checks; a bad or unfinished file is refused whole, naming the line.
- **Phase 20, Meta Pixel and Conversions API** (plugin `meta-capi`, **Marketing → Meta tracking**):
  - Facebook and Instagram ads get PageView, ViewContent, AddToCart, InitiateCheckout and Purchase from the server (they arrive even with ad blockers) and, if the store wants, from Meta's Pixel in the browser too; each event has one ID, so Meta counts it once. Meta's script loads only after the page is ready, so it doesn't slow the store down.
  - **When to send Purchase**: when the order is placed, confirmed by staff (the default) or delivered, so ads learn from real buyers rather than fake COD orders. Customer details are hashed; placeholder emails are never sent; imported orders never count, phone and Messenger orders only if the store says so.
  - Up to two Pixels, each with its Conversions API token (encrypted, never shown again), "Send test event", a test event code for Meta's Test Events tool, and an event log with what was sent and Meta's answer. A token Meta refuses shows a warning; events wait up to 7 days for a new one.

- **Phase 19, couriers: Steadfast and Pathao** (plugin `couriers`):
  - **Book courier** on the order page (with the store's courier for the delivery zone, or another), or for many selected orders at once from the order list. A confirmed order is packed first. Clicking twice never books twice.
  - The courier's updates move orders: picked up → Shipped, delivered → Delivered (the COD payment is marked received), returned → Returned. By webhook (Settings → Couriers shows the address and secret to paste into each courier's panel) and every 30 minutes by asking the courier.
  - Stickers print the courier's consignment barcode; the customer's tracking page links to the courier's tracking page; the home page shows parcels with couriers, delivered today and returned this week.
  - Pathao's cities and zones are matched to our districts and thanas by name; **Orders → Unmapped addresses** lists the thanas it couldn't match, to choose once.
  - When a courier is down: "Booked by hand" with the courier's name and tracking code. A booking cancelled in the courier's panel can be marked cancelled here before pickup; a booked order can't be edited or cancelled until then.

- **Phase 18, online payments: SSLCommerz and bKash** (plugin `payments-online`):
  - Shoppers can pay online at checkout (card, mobile banking or net banking through SSLCommerz, or bKash), in full or just the advance with cash on delivery for the rest. The order is placed at once, waiting for payment ("Awaiting payment"): it has its number and holds its stock, but isn't in the confirmation queue until the gateway confirms the money.
  - Only the gateway's own server-to-server answer marks an order paid (SSLCommerz validation API with `val_id`, bKash execute and query); every unfinished payment is checked again every 5 minutes for a day, then hourly for a week, so a payment without a notification is still found.
  - Unpaid online orders are cancelled after 45 minutes (a setting), releasing stock. The tracking page shows "Pay now" until then, and says why a bKash payment failed.
  - **Orders → Payment reviews**: money paid late, paid twice, flagged as risky, or with the wrong amount waits for a person to accept, refund through the gateway, or mark resolved. Each order shows its online payment tries with "Check status now".
  - **Settings → Online payments**: on/off, sandbox or live, credentials (encrypted with the new `SECRETS_KEYRING`, never shown again), Test connection, the time to pay. A gateway that keeps failing is hidden at checkout for a few minutes; cash on delivery still works.
  - The "order placed" SMS for an online order is sent once it's paid.

- **Stores on CloudPanel without a shell** (`ops/cloudpanel/ecommbd-stores`, runbook `docs/runbooks/cloudpanel-stores.md`): support creates a Node.js site with an App Port from 4301 to 4399 in CloudPanel, and within a minute the server sets it up (PostgreSQL database, settings, core, worker and storefront services, a login file in the site's File Manager). Admins install it once per server and update every store with `ecommbd-stores deploy` (database dump, restart, health check) or go back with `rollback`. Set up on host2 and tested with store1.ecomm.bd.
- `ASSETS_DIR` setting for the uploads folder, so stores can share one build. The built storefront, with `PROXY_CORE=true`, also passes the merchant admin, the Dashboard, their APIs and `/bd-geo` to the core.
- **Phase 17, the storefront speed layer:** Varnish in front of the storefront (`infra/varnish`, `docker compose --profile speed`), and a core plugin, `cache-purge`, that purges exactly what changed. A product edit refreshes its own pages and the listings, not content pages, and shows within 3 seconds; listings get a second refresh once the search index has caught up. Stock purges only when "in stock", "only a few left" or "sold out" changes; promotion starts and ends are scheduled; an import purges once, at the end. Personal pages, sessions and previews are never cached, and random query parameters can't fill the cache. After a purge-all or a Varnish restart, the worker warms the top pages through the store's public address. A sampled speed beacon (a 368-byte loader) reports real-user LCP, INP and CLS, with nothing about the visitor stored. size-limit and Lighthouse budgets run in the speed suite (`npm run test:speed`) and CI. Fixed after review the same day (precise tags, one delivery loop, no purge on restart, warm-up keys, beacon limits, bilingual 503, purge-port check, tests that check what they claim). [Notes](docs/roadmap/phase-17-implementation.md), [test results](docs/runbooks/phase-17-test-results.md), [cache runbook](docs/runbooks/storefront-cache.md). Production install and Bangladesh field measurements: phases 23–29.
- **Phase 22, WordPress helper and cutover** (`apps/wp-migrator`, plugin `woo-import`):
  - A WordPress plugin that sends the store's data to us. The merchant pastes a one-time pairing code (valid for an hour); after that, every upload is signed, encrypted at rest, and can be resent safely after a timeout. The plugin opens nothing on the merchant's site.
  - Customers keep their WordPress passwords: the first successful login checks the old hash (phpass, WordPress 6.8's `$wp` bcrypt, plain bcrypt, old MD5), then saves our own hash and deletes the old one. A password reset ends the old password for good.
  - Coupons, SEO titles and descriptions, approved reviews (kept privately for phase 35), and the store's settings for reference (the Pixel ID waits for phase 20).
  - Old addresses: product and category links with the store's own bases, image pages, `?p=` and `?product=` links, WordPress pages and Redirection-plugin rules, a list of the most-asked-for missing pages, and a sitemap checker. A cutover checklist and a private export of new orders for a rollback.
  - [Plan](docs/roadmap/phase-22-implementation.md), [test results](docs/runbooks/migration-test-results.md), [cutover runbook](docs/runbooks/cutover.md). Still open: a rehearsal with a real merchant's store, and the domain switch.
- **Phase 21, WooCommerce migration through the REST API** (plugin `woo-import`):
  - Connect with read-only API keys (kept encrypted), look at the store, then a dry run that lists what will be skipped and why, before anything is written.
  - Imports categories, tags, simple and variable products with their options, images (through the safe download checks of phase 09), customers by phone, and the full order history exactly as WooCommerce recorded it, in a separate read-only archive. Reviewed recent unpaid COD orders can become real orders.
  - Safe to run again (it updates, never duplicates) and resumes where it stopped. A report compares counts, monthly totals and 20 sample orders. English and Bangla screens; old orders show on the customer's page.
  - [Plan](docs/roadmap/m5-implementation.md), [manual acceptance checklist](docs/runbooks/migration-testing.md).
- **Phase 16, sales pages, the Design tab and attribution** (plugin `bd-sales-pages`):
  - **Sales pages** (a menu of its own): pages for Facebook ads at `/s/<address>/`, one product with its offer and an order form on the same page. A new page starts from a name, a product and one of twelve Bangla templates (ghee and honey, oil and spices, dates, herbal, skin care, perfume, a single garment, garments with a size chart, gadget, baby product, seasonal combo, general) and fills itself with the product's name, photo, price, video and review screenshots. The list shows each page's address, template, product, price, status (live, off, not published, product deleted) and the orders it brought, with preview, open, edit, duplicate and delete.
  - Sales page settings in the editor: address, product, on/off; **packs** (1, 2, 3… at their own prices, one marked popular) and an **add-on offer** (another product at a special price, a tick box in the order form, hidden when out of stock); the slim header with logo and phone (or the store's header, or none), a small footer, a phone-width column, the page's own colours and font; the thank-you message, a WhatsApp button and an optional move on to another page of the store; search engine fields with **hide from Google** on by default; an order bar at the bottom on phones.
  - New sections: sales hero (headline with a coloured second line, badge, photo or video, the offer), benefits, specifications or steps, price and packs, comparison (without / with), countdown (to a date in Dhaka time, or a few hours for each visitor), guarantee and the **order form**: pack and variant, the add-on, name, phone, district → thana, address, delivery charge, cash on delivery or mobile banking, the SMS code when needed, and the total on the button. It uses the checkout's own checks, in a session of its own, so the shopper's cart is left alone; it works without JavaScript. Any section can have an "Order now" button below it on a sales page.
  - **Design tab** on every section, on every page: any background, text and button colour, space above and below (and on phones), content width, corners, border, heading size (and on phones) and weight, text size and the image shade. And a **Custom section**: one to four columns of headings, text, images, buttons, checklists, icon boxes, video, countdowns, prices, badges, stars, spaces and lines, each styled on its own. The styles become one small stylesheet per page, allowed by its hash in the Content Security Policy.
  - Prices of packs and add-ons come from an automatic **"Sales page offer"** promotion, worked out in the core from the page's settings; the browser never sends a price.
  - **Attribution:** every page notes the ad or link a shopper came from (UTM values, Facebook, Google and TikTok click IDs, the referring site, the sales page) for 30 days, the last non-direct visit winning; every order placed on the store or a sales page keeps it. Orders filter by campaign and sales page, the order screen shows **Where it came from**, and **Orders → Orders by campaign** counts orders per campaign and page.
  - Tests: unit tests of the Design options, generated styles, Custom section, sales sections, templates, page settings, offer prices and attribution; end-to-end tests of sales pages, offers, attribution and filters; Playwright tests of making and publishing a page in the admin, ordering with and without the add-on and without JavaScript, attribution, stock limits and the budget of every template; 72 new visual snapshots.

- **Phase 15, sections, themes and the page editor** (plugin `bd-sections`, package `packages/sections`):
  - Merchants design the home page, the product page (sections below every product) and each page without code, in a full-screen editor in the merchant admin: the page's sections on the left (drag or arrow keys to reorder, hide without deleting, duplicate, save for reuse, remove), the real storefront in the middle showing the draft (phone view first, computer view a tap away), and the selected section's settings on the right, in Bangla and English. Tap a section in the preview to edit it. Undo and redo, autosave, publish, the last 20 published versions with one-click restore, and a 30-minute preview link to send to a partner on WhatsApp. On a phone, sections and preview are two tabs.
  - 18 sections: hero, slideshow, offer banner, product grid (newest, best selling, a category or hand-picked), category list, featured product, image with text, rich text, columns, FAQ, image gallery, video (YouTube or Facebook, loads only when played), customer reviews (cards or screenshots), trust badges, delivery information, contact, order on WhatsApp and divider. Each has a few preset style options: background, text colour, space, width, alignment, hide on phones or computers, an ID buttons can jump to, and one fade-in.
  - Four templates for Bangladeshi shops (fashion, food, gadgets, cosmetics) that fill themselves with the store's own products and categories.
  - **Online store → Theme**: two themes, Minimal and Bazaar (denser, bolder, the brand colour in the header), with colours (text must stay readable), font (the phone's own, Hind Siliguri or Noto Serif Bengali, self-hosted), button style, header layout, product cards, logo size and the announcement bar; changes show in the preview before saving. Switching themes keeps every page as it is.
  - Two staff editing one page are told who changed it ("A newer version was published by Rahim") and choose to reload or keep their own.
  - Publishing updates the live page within seconds (the storefront's cache is purged); pages carry `xkey` tags for phase 17. Missing products, categories or images are pointed out in the editor and never break the page.
  - New permission `EditStorefront` (owner, manager, marketing); new storefront setting `EDITOR_ORIGIN` (development only).
  - Tests: unit tests of the section schemas, data migrations, themes and contrast checks; end-to-end tests of drafts, conflicts, publishing, history, preview tokens, saved sections, page copies, the theme and permissions; Playwright tests of building and publishing a home page, reordering, hiding and undo, restoring a version, two staff publishing at once, the theme screen, shared previews, the phone editor, the product template and the JavaScript budget of every template; visual snapshots of every section (`npm run test:visual`).

- **Phase 14, cart, checkout and order tracking** (storefront; plugin `bd-tracking`):
  - Product pages have a buy form: choose the size or option, the quantity, then **Add to cart** (a slide-out cart opens in place) or **Buy now** (straight to checkout). The header shows how many items are in the cart without making pages uncacheable.
  - A one-page checkout in Bangla and English: name, mobile number (the operator shows as you type), district and thana (both languages), address; delivery choices and the "spend ৳X more for free delivery" hint; cash on delivery (with the COD charge and any advance), or bKash, Nagad or Rocket with the merchant's number, sender and TrxID; the SMS code when the store asks for it; a summary of what's paid now and on delivery. It works without JavaScript too.
  - One order per tap, even with double taps or retries on a slow connection. A changed price or delivery charge is shown before ordering; an item that sells out meanwhile leaves the cart with a message. The back button after ordering shows the order, not an empty checkout.
  - A thank-you page with the order number, next steps, a WhatsApp button and a tracking link.
  - Order tracking at `/track/` (order number and phone, posted, never in the address) and from the SMS link `/t/<token>`: status timeline, first name, district and items only; limited tries per address and per phone.
  - New settings: `CSRF_SECRET` (storefront; required in staging and production) and `TRACKING_RATE_LIMIT_PER_IP` (core).
  - Tests: end-to-end tests of tracking; unit tests of the session relay, CSRF and form timing; Playwright tests of COD with and without JavaScript, Nagad, a bKash advance, the SMS code, double submits and retries, price and stock changes, tracking, guessing protection, accessibility (axe), the JS budgets (3.4 KB on checkout, 6.1 KB on product pages) and a checkout on a throttled phone (5.9 s).
- **Phase 13, catalog browsing, search and filters** (plugin `bd-search`; storefront redesign):
  - Search that finds products in Bangla, English or with a typo: "পাঞ্জাবি", "panjabi" and "punjabi" find the same panjabi; "শাড়ী" finds "শাড়ি"; "ঘি ৫০০" finds "ghee 500". Every word must match, in any language of the product (name, variations, SKU, sizes and colours, tags, categories). "Did you mean" corrects typos; sold-out products come last; a search that finds nothing shows popular products.
  - Category and search pages with filters: size and colour (from the product form's variations), tags and other facets, price range and "in stock only", with counts; orders Featured, Newest, Price low to high and high to low, Best selling; numbered pages. A category also lists its subcategories' products, featured products first. Filters work without JavaScript; with it they apply at once on desktop and open as a panel on phones. Each filter state has one address (one 301 for any other spelling); filtered pages aren't indexed.
  - Search suggestions under the search box (categories and products with photo and price), with the keyboard; the script loads only when the box is first used.
  - Merchant admin: **Online store → Search**: synonyms (`panjabi, পাঞ্জাবি, punjabi`; a starter list for new stores) and the searches that found nothing in the last 30 days, with "Add as synonym".
  - The storefront restyled to a Shopify-like standard (written down in `CLAUDE.md`): neutral colours, square corners and no pill shapes, our own icons (no icon library), borderless product cards with Sale, Sold out and New labels and the old price struck through, an announcement bar, a phone menu, a light footer, smooth page changes; motion is off for shoppers who prefer less.
  - Rate limits on search per shopper address (`SEARCH_RATE_LIMIT_PER_MINUTE`, default 600 a minute).
  - Tests: a relevance suite of 67 queries on a 200-product Bangla/English catalogue; unit tests for text matching and filter addresses; end-to-end tests of search, filters, suggestions, synonyms, searches with no results, permissions and rate limits; Playwright tests with JavaScript on and off, desktop and phone, and server time on 500 products.
- **Phase 12, storefront foundation** (new app `apps/storefront`, plugin `bd-content`):
  - The shop in Bangla and English, server-rendered with Astro and no JavaScript: home, nested categories with pagination, product pages (photos, variations, price ranges, stock, an "Order on WhatsApp" link), content pages, the four policies, search, and the cart, checkout, account and tracking addresses for the coming phases.

Any other spelling of an address, including an old slug or another Unicode form of a Bangla slug, gets one 301 to the right one. Deleted products answer 410 with suggestions.
