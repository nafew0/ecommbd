# Decisions

A short log of decisions and why. Newest at the bottom. Details live in [architecture.md](architecture.md) and the [roadmap](roadmap/README.md).

| Date | Decision | Why |
|---|---|---|
| 2026-10-20 | **Vendure 3.8 is the core**, installed from npm and extended with plugins, staying on upstream releases | Won the benchmark against Medusa ([bench/RESULTS.md](../bench/RESULTS.md)); upgrades stay a version bump |
| 2026-10-20 | **One isolated site and PostgreSQL database per store**, on our CloudPanel servers | Isolation between stores, "your store isn't locked into a platform" pitch |
| 2026-10-20 | **PostgreSQL + two Redis (queue, cache) + Varnish** per server | Speed; Redis queue must never evict jobs, cache must |
| 2026-10-20 | **Astro + Preact islands** for the storefront | Zero JavaScript by default: the fastest option |
| 2026-10-20 | **Keep tooling simple for the MVP:** ESLint (recommended rules) + Prettier, Vitest, Playwright, one CI job, Dependabot | The user's call: easy to understand and maintain. Stricter checks (permission audit test, audit gates, CodeQL, secret scanning job) can be added later if needed |
| 2026-10-20 | **TypeScript 5.8.2**, not the newer 7.x | It's the version Vendure 3.8 is built and tested with |
| 2026-10-20 | **Known dependency advisories accepted for now.** `npm audit` reports 13 high-severity advisories in Vendure 3.8's dependencies; none can be fixed without a newer Vendure. Most are build tooling (`braces`, `micromatch`, `ts-morph`, `lingui`), not reachable by shoppers | **Must fix before phase 10** (real customer emails): nodemailer's address-parser denial-of-service. Upgrade Vendure if a fix exists by then, otherwise validate email addresses strictly before they reach nodemailer |
| 2026-10-20 | **Idempotency stores must claim keys atomically** (Redis `SET NX`, a database unique constraint) | A test caught the in-memory store letting two identical requests both run; fixed |
| 2026-10-21 | **Our own simple merchant admin** (`apps/admin`, React, Bangla and English) on Vendure's Admin API, built from phase 02b. Vendure's Dashboard stays for our support team only. Replaces the plan to reskin Vendure's Dashboard to look like WooCommerce | Our partner wants a simple admin with only the fields BD merchants use, modelled on a working BD store ([research/reference-bd-admin.md](research/reference-bd-admin.md)). Vendure's Dashboard is built for complex stores and has no Bangla. Cost: we build each screen ourselves |
| 2026-10-21 | **Place data (phase 02): official BBS geocodes, Bangla names from an MIT dataset, metro thanas added by us.** `packages/bd-geo`: 8 divisions, 64 districts, 495 upazilas and 12 city corporations from the BBS geocodes OCHA publishes on HDX (CC BY-IGO, valid from 2023-05-20); Bangla names from `nuhil/bangladesh-geocode` (MIT); Dhaka's 50 and Chattogram's 15 metropolitan thanas compiled by us. IDs are the official P-codes (`BD3026`, `BD30260072`); ours contain an `M` (`BD3026M26`). IDs are never reused | Official and attributable, and it includes the upazilas created in 2021–22. No open dataset had good metro thanas, so we keep our own list and version it (`dataVersion`, data CHANGELOG). Other cities' metro thanas can be added later |
| 2026-10-21 | **No Vendure provinces for districts.** Districts and thanas live in bd-geo and in address custom fields; the server fills Vendure's `province` (district) and `city` (thana) in English from the IDs | One source of truth. Vendure doesn't match addresses to provinces in zones by itself, and our shipping zones (phase 07) use bd-geo's delivery-zone tags |
| 2026-10-21 | **Address mapping:** `streetLine1` = house/road/village; custom fields `districtId`, `thanaId`, `area`, `landmark`, `alternatePhone` (E.164). Checked server-side for every address mutation (customer, order, draft order, order edits): district and thana together, the thana in the district, "other" only with an area | Vendure 3.8 copies Address custom fields onto order addresses (`OrderAddress`, `UpdateOrderAddressInput`), checked in its source and by an end-to-end test. One check covers every API path, including the Dashboard |
| 2026-10-21 | **Default storefront language:** `STORE_DEFAULT_LANGUAGE` (default `bn`) is used once, when a store is set up; afterwards the merchant changes it in Store settings, which updates the channel | Provisioning (phase 24) sets it per store; the merchant stays in control |
| 2026-10-21 | **Prices always include tax.** Default tax: category "Standard", 0% in zone Bangladesh. Our admin offers no tax-exclusive pricing, and the settings page warns if the channel was changed to it or away from BDT. Rounding stays as in the roadmap (whole taka, half-up at line level), applied in phases 07–08 | How BD shops price. VAT-registered merchants set their own rate with their accountant |
| 2026-10-21 | **Store settings in Vendure's settings store** (`bdStore.settings`), written only by `updateBdStoreSettings` (new permission `UpdateStoreSettings`), validated by one zod schema shared with the admin, with the last 50 changes kept (who, when, which fields; no values). Private: the owner's mobile; everything else is public. The Shop API has its own typed schema without private fields | The settings store fits (JSON, permissions, scopes) and needs no new table. A separate typed Shop schema makes leaking a private field impossible, not just untested |
| 2026-10-21 | **Store defaults initializer:** runs on every server start and with `npm run store:init` (`--force` for operations staff). Each step runs once, is recorded, and runs in its own transaction under a PostgreSQL advisory lock. Later phases add steps with `registerStoreDefaults`; to change a default for existing stores, add a new step | Never fights a merchant's changes; safe after an interruption and with several processes starting at once |
| 2026-10-21 | **Staff roles defined now:** Owner, Manager, Order staff, Packer, Marketing (permission sets in `bd-core/store-defaults/roles.ts`). Assigning staff comes in phase 32 | Matches the spec's P1 roles; the server enforces them from day one |
| 2026-10-21 | **Merchant admin stack:** React 19, Vite 7, Tailwind 4, TanStack Query, React Router 7, lucide icons. shadcn-style components built on native elements (`<dialog>`, `<select>`) rather than Radix. No translation library: typed `bn`/`en` dictionaries, so a missing Bangla string fails the type check. Hind Siliguri self-hosted (Fontsource, OFL), two weights | Same family as Vendure's Dashboard, but smaller: native elements inject no styles (strict CSP) and use the phone's own pickers. First load ≈ 126 KB gzipped JS; each screen loads when opened |
| 2026-10-21 | **Admin served by the core at `/admin`** (same origin as the Admin API). HTTP-only session cookies with separate names (`admin-session`, `shop-session`), SameSite=Lax, Secure in staging and production; Vendure's `csrfPrevention` on; strict CSP on `/admin`. The admin accepts PNG, JPG and WebP uploads only (no SVG until phase 09's upload checks) | No CORS, no tokens in JavaScript. Separate cookie names stop a storefront sign-in from replacing an admin session on the same domain |
| 2026-10-21 | **Geo lists are also plain GET routes** (`/bd-geo/districts`, `/bd-geo/districts/:id/thanas`) with Cache-Control and an ETag on the data version, next to the `bdDistricts`/`bdThanas` GraphQL queries | GraphQL POSTs aren't cached by browsers or Varnish. **Open item:** there is no general rate limit on public endpoints yet; it arrives with the server baseline (phase 23, nginx) and hardening (phase 30) |
| 2026-10-21 | **Phase 02 edge cases without their own test:** language fallback for products without Bangla (Vendure's built-in fallback; there are no products until phase 05); the initializer before a WooCommerce import (phase 21 tests it); long Bangla labels are covered by the phone-width "no sideways scrolling" browser test rather than a visual check | Each belongs to a later phase or is Vendure's own behaviour |
| 2026-10-21 | **Phase 03, names:** the full name as typed goes in Vendure's `firstName`, and `lastName` stays empty (Vendure accepts it). Each order's shipping address keeps the name typed for that order; the customer record's name comes from the first order and is never overwritten | We never split Bangla names into first/last; one phone shared by a family stays one customer with each order's own name |
| 2026-10-21 | **Phase 03, phone identity:** customers are found by the custom field `phone` (E.164, unique index). New guests get the placeholder email `<digits>@phone.invalid` (`.invalid` can never receive mail); `isPlaceholderEmail()` in `packages/shared` hides it everywhere. A deleted customer's phone is cleared, so the number can start a new customer. Two checkouts creating the same new phone at once: the customer is created in its own short transaction, and the unique-index error re-reads and attaches the customer that won | One record per phone, safe under concurrency without locks held for the whole checkout |
| 2026-10-21 | **Phase 03, guests and registered phones:** guest checkout with a registered customer's phone (or email) is allowed and links the order to that customer for history and stats. In the Shop API, a guest's `Order.customer` is a stand-in built only from what was typed for this order (name and phone; no account ID, email, saved addresses or user), so nothing reveals whether a phone has an account. Vendure's `setCustomerForOrder` (older clients) uses our guest-checkout strategy: it finds by phone, then email, and never updates an existing customer | COD shoppers often forget they registered; showing account data to anyone who types a phone number would leak it |
| 2026-10-21 | **Phase 03, errors and guard:** checkout mutations return Vendure-style error results (`BdCheckoutError` with a `code` such as `INVALID_PHONE`) whose message is translated from `errorResult.BD_CHECKOUT.<code>` in the request's language. The "valid phone and BD address before payment" guard is in the order process (`onTransitionStart` to `ArrangingPayment`), which also covers older clients and admin draft orders | Typed codes for the storefront, readable Bangla/English messages; Vendure's order interceptor only covers adding and changing lines |
| 2026-10-21 | **Phase 03, customer stats** (orders, delivered, returned, cancelled, total spent, last order) are recomputed from the orders table on order events, not incremented. Total spent counts delivered orders only | Recomputing is correct after retries, out-of-order events and imports; for COD, money is only received on delivery |
| 2026-10-21 | **Phase 03, checkout settings** (show email, alternate phone and note; minimum address length, default 10 characters; international phones, default off) live in the settings store (`bdCheckout.settings`), validated by a zod schema in `packages/shared`, changed with `UpdateStoreSettings`. The storefront reads them from the Shop API. The admin screen comes with the checkout UI (phase 14, as the menu plans) | Nothing uses them visibly before the storefront exists |
| 2026-10-21 | **Phase 03, rate limits:** fixed windows in the cache Redis (an atomic `INCR` script, keys under the store prefix), per session and per phone, on both checkout mutations; `RATE_LIMITED` tells the shopper to wait. Limits are plugin options | Stops phone probing and spam carts without punishing shoppers who share an IP (carrier-grade NAT) |
| 2026-10-21 | **Phase 03, email hygiene now:** the default email handlers are wrapped so a placeholder recipient is never emailed. The rest of email hygiene (real transport, no `/mailbox` in production) stays in phase 10 | Vendure's order confirmation would otherwise try to email `…@phone.invalid` from the first COD order |
| 2026-10-21 | **Phase 03, customer note** is sent with `setOrderShippingAddressBD` (`note`), since the storefront sends delivery details together; the order's `locale` is the request's language when the shopper sets their phone | One call for the delivery step, and SMS (phase 10) knows the shopper's language |
| 2026-10-21 | **Phase 04, order statuses:** New = `PaymentAuthorized`/`PaymentSettled`; our order process adds `Confirmed`, `Packed` and `Returned`; Shipped, Delivered and Cancelled are Vendure's. Every allowed transition is in [decisions/order-states.md](decisions/order-states.md); anything else between placed states is refused. An order counts as placed with Vendure's default strategy (checkout completes, COD included) | Vendure's extension point; one shared table drives the server guard and the admin buttons |
| 2026-10-21 | **Phase 04, order numbers:** custom field `orderNumber` from the PostgreSQL sequence `bd_order_number_seq` (starting at 1001), assigned in the order process at placement, in the same transaction; the optional prefix from order settings gives `MF-1001`. Vendure's random `code` stays for carts and links. A number is lost only if a placement fails after drawing it (sequences don't roll back); abandoned carts never take one | Safe under concurrency without locking; merchants and couriers see short numbers |
| 2026-10-21 | **Phase 04, confirmation queue:** an indexed custom field `confirmQueueAt` orders the queue: set at placement, "No answer" moves it to now (bottom of the queue), "Call later" to the chosen time (hidden until then), cleared when the order leaves New. Imported orders never enter it. Call attempts are order history entries (`BD_CALL_ATTEMPT`) with outcome, staff and time. This index replaces the planned (state, placedAt) index: Vendure custom fields can't declare composite indexes, and TypeORM would drop a hand-written one at the next `migrate:generate` | One small index serves the hot query at Eid volume |
| 2026-10-21 | **Phase 04, two staff on one order:** every action locks the order row (`SELECT … FOR UPDATE`) and compares the status the staff member saw; the second gets `ALREADY_CHANGED` with who and when (from Vendure's history), e.g. "Already confirmed by Karim 1 minute ago". Claims ("Rahim is calling") are order fields valid for 5 minutes, shown to others but not blocking | The lock makes the check-and-change atomic; claims only prevent double calls, so a stale claim never blocks work |
| 2026-10-21 | **Phase 04, cancelling:** needs a reason code (fake, customer cancelled, unreachable, duplicate, out of stock, price issue, other; "other" needs a note). Orders with money received (a settled payment) are refused with `REFUND_REQUIRED` until phase 08 adds refund records | Reasons feed the fraud score (phase 11); money must never vanish silently |
| 2026-10-21 | **Phase 04, shipping before couriers:** staff mark orders shipped, delivered or returned by hand (a manual fulfillment for all lines); phase 19 does it from courier bookings | Merchants can use the workflow end to end before courier integrations |
| 2026-10-21 | **Phase 04, payment type** is derived from payments: prepaid (settled ≥ total), advance (something settled), COD (nothing settled) | Works unchanged when phase 08 adds COD and manual mobile banking |
| 2026-10-21 | **Phase 04, permissions:** `ConfirmOrder` (confirm, call attempts, claims), `CancelOrder`, `PackOrder`, `ReadSalesFigures`; marking shipped, delivered or returned uses Vendure's `UpdateOrder`. A new store-defaults step grants them to the default roles: Owner and Manager all; Order staff confirm and cancel; Packer pack; Marketing sales figures | Order staff confirm without seeing sales totals; existing stores get the permissions without editing the phase 02 roles step |
| 2026-10-21 | **Phase 04, other details:** home widgets count the Dhaka day (orders placed today that aren't cancelled; sales need `ReadSalesFigures`); a second order from the same customer with the same items within 30 minutes is flagged "possible duplicate" with a one-click cancel; the auto-cancel suggestion (off by default) only flags orders, and cancels by itself (hourly, reason "unreachable") only when the merchant turns that on too. Events `BdOrderConfirmedEvent`, `BdOrderPackedEvent`, `BdOrderReturnedEvent` and `BdOrderCancelledWithReasonEvent` carry the acting staff member and never fire for imported orders | As the roadmap asks; each is small and tested |
| 2026-10-21 | **Open item, found in phase 04:** Vendure stores dates in PostgreSQL `timestamp` columns (no time zone) in the Node process's local time. PostgreSQL's own defaults (every `createdAt`) write UTC, so on a machine set to Dhaka time the two disagree by 6 hours (the order history showed "6 hours ago" for a new order). **Fixed:** the core sets `TZ=UTC` for itself (`src/env.ts`), and so do the test configs; the database now holds UTC, as the product standard says. SQL written by hand still passes JS dates. Dev data saved before this fix is 6 hours off; production has none | Found by the Dhaka day-boundary test and a screenshot on a developer Mac set to Dhaka time |
| 2026-10-21 | **Phase 06, rendering:** print views are HTML pages in the merchant admin, printed by the browser; no server-side PDF library. A spike rendered the same Bangla text with pdfkit and with Chrome: pdfkit shaped the conjuncts but has no font fallback (the comma in "৳১,২৫০" came out as a missing-glyph box), while the browser shapes with HarfBuzz and falls back per character. Page sizes are set from script with a constructed stylesheet, which the admin's strict CSP allows (it blocks inline `<style>`) | Correct Bangla on every staff PC, no PDF work on the server, and Chrome's "Save as PDF" still gives a PDF |
| 2026-10-21 | **Phase 06, barcodes:** our own Code 128 encoder in `packages/shared` (code sets B and C, about 100 lines with the published pattern table) drawing SVG, rather than a library (`bwip-js` is large; `JsBarcode` is fine but more than we need). Every barcode is checked by decoding it with ZXing (Apache-2.0) in unit and browser tests; ZXing and `pngjs` (MIT) are dev dependencies only | No runtime dependency, works in the browser and on the server, proven scannable by an independent decoder |
| 2026-10-21 | **Phase 06, structure:** printing is its own plugin, `bd-print`, not part of `bd-orders`, so it doesn't touch the files Imtiaz's phases change. One query, `bdPrintData` (permission `PrintOrders`, at most 100 orders, `Cache-Control: no-store`), returns exactly what a document shows: packing slips carry no prices from the server. Each order remembers when its invoice (or receipt), packing slip and sticker were last printed; a later print says "Reprint" | Fewer merge conflicts between the two branches; the role check and the "no prices" rule live on the server |
| 2026-10-21 | **Phase 06, layout:** invoices A4 or A5, packing slip, 80 mm receipt; stickers 4×6 in, 3×4 in, and A4 sheets of 8 (2×4, 105×74 mm) or 12 (3×4, 70×74 mm) labels, a starting point since label sheets vary. Multi-page invoices are paginated by measuring each line, so "page 2 of 3" counts one invoice (CSS page counters would count the whole print job). Sticker addresses shrink to a minimum size, then wrap; phone and COD amount sit outside the shrinking area so they are never cut off. Font: Hind Siliguri, already self-hosted with its Bengali and Latin subsets | As the roadmap asks; measured pagination works the same in every Chrome |
