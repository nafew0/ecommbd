# Ecomm BD setup guide

[![CI](https://github.com/nafew0/ecommbd/actions/workflows/ci.yml/badge.svg)](https://github.com/nafew0/ecommbd/actions/workflows/ci.yml)

**Ecomm BD** is a hosted ecommerce platform for Bangladesh. It's built for WooCommerce merchants who are tired of hacked sites, nulled plugins and update headaches. Each store runs on its own isolated site and database, with Bangladesh's essentials built in: cash on delivery, bKash and Nagad, couriers, SMS, and Meta's server-side tracking. The motto: *fastest ecommerce website in BD*. What it does is in the [MVP spec](docs/mvp-spec.md), and the build plan is in the [roadmap](docs/roadmap/README.md).

This README is the setup guide for developers.

> Vendure 3.8.0 · Node.js 24 · Companion to [architecture.md](docs/architecture.md), [mvp-spec.md](docs/mvp-spec.md) and the [roadmap](docs/roadmap/README.md)
> Last verified 2026-10-20 on macOS (Apple M4), Node 24.16, npm 11.16, Docker 29.8. Sections 2–5, 7 and `npm run doctor` were run as written. Sections 1 (GitHub), 6 (`vendure add`) and 9 (upgrade) follow Vendure's and GitHub's docs but haven't been run here yet.

## How this project uses Vendure

Vendure is our commerce core: customers, auth, admin roles, products, stock, cart, checkout, orders, promotions, assets, search, job queue and the Dashboard. We **reuse all of it** and add only what Bangladesh stores need.

- **Vendure comes from npm, not copied into our repo.** `apps/core` is a standard Vendure project generated by `@vendure/create`, so Vendure's docs and CLI work on it unchanged.
- **Our features are Vendure plugins** in `apps/core/src/plugins/`.
- **Upgrading Vendure is a version bump**, which is how we stay on upstream releases (section 9).

When something must change, use the first option that works:

| Order | Way to change behaviour | Example |
|---|---|---|
| 1 | Vendure configuration and its built-in strategies | Custom order states (`OrderProcess`), payment handlers, shipping calculators, auth strategies |
| 2 | Our own plugin | Courier booking, Meta Conversions API, phone-only checkout |
| 3 | A small patch to Vendure's published code (`patch-package`) | Only when 1 and 2 can't do it. Every patch is documented |
| 4 | Building Vendure from our GitHub fork | Last resort, if patches pile up (section 9) |

## 1. GitHub repositories

### 1a. The project repository

From the project folder. First remove `bench/medusa/.git`, which is left over from cloning Medusa's starter for the benchmark; otherwise git treats `bench/medusa` as an embedded repository:

```bash
rm -rf bench/medusa/.git
git init
git add .
git commit -m "Initial project setup"
gh repo create <your-org>/ecommbd --private --source . --push
```

`.env` files are git-ignored. Each developer creates their own from `.env.example` (step 3).

### 1b. Fork Vendure

We don't run Vendure from the fork. It's our copy of the source:

- to read and debug the exact version we run
- to prepare fixes we send upstream as pull requests
- as the starting point if we ever need option 4

From the folder that *contains* `ecommbd`:

```bash
gh repo fork vendurehq/vendure --org <your-org> --clone
```

This creates `<your-org>/vendure` on GitHub and clones it into `./vendure`, with `origin` pointing at your fork and `upstream` at `vendurehq/vendure`. To look at the code we run:

```bash
cd vendure
git fetch upstream --tags
git checkout v3.8.0
```

Keep the fork's default branch current:

```bash
gh repo sync <your-org>/vendure --source vendurehq/vendure
```

## 2. Start PostgreSQL and Redis

```bash
nvm use
npm run services:up
```

This starts the services in the root `docker-compose.yml`, which mirror the production setup in architecture.md (Decisions 4 and 5).

| Service | Port | Purpose |
|---|---|---|
| PostgreSQL 17 | 54320 | Database `ecommbd`, user `ecommbd`, password `ecommbd` |
| `redis-queue` | 63790 | BullMQ job queues: `noeviction`, append-only file on |
| `redis-cache` | 63791 | Vendure cache: `allkeys-lru`, no persistence |

The ports are offset so they don't clash with a PostgreSQL or Redis already on your machine. `npm run services:down` stops them and keeps the data.

## 3. Install and configure

```bash
npm install
cp apps/core/.env.example apps/core/.env
```

In `apps/core/.env`, set `COOKIE_SECRET` to a random value:

```bash
openssl rand -hex 32
```

The other defaults match the Docker services. `APP_ENV=dev` allows the default `superadmin` / `superadmin` login. `STORE_DEFAULT_LANGUAGE` (`bn` or `en`, default `bn`) is the storefront's main language for a new store; it's used once, when the store is set up.

The server checks every setting when it starts (`apps/core/src/env-schema.ts`). If one is missing or wrong, it stops and lists them, for example `COOKIE_SECRET: must be at least 32 characters`. In staging and production it also refuses the default admin password, and requires `REDIS_KEY_PREFIX` and `ASSET_URL_PREFIX`.

## 4. Run in development

```bash
npm run dev
```

This builds the shared packages and the merchant admin, then runs Vendure's `vendure dev all`: the server, the job worker and the Dashboard. Pending database migrations run automatically on start (`runMigrations` in `src/index.ts`). The server answers its health check about 10 seconds after start.

- On the very first start, the worker logs `Awaiting DB schema creation…` a few times while the server creates the tables. That's normal.
- The Shop and Admin APIs are GraphQL endpoints that answer POST requests; opening them in a browser shows a 400.
- In dev the Dashboard comes from Vite with live reload. `:3000/dashboard` passes through to it, and it's also on http://localhost:5173/dashboard.

| What | URL |
|---|---|
| Merchant admin (Bangla and English) | http://localhost:3000/admin |
| Vendure Dashboard (our support team) | http://localhost:3000/dashboard |
| Shop API (storefront) | http://localhost:3000/shop-api |
| Admin API | http://localhost:3000/admin-api |
| GraphiQL (dev only) | http://localhost:3000/graphiql/shop and /graphiql/admin |
| Test mailbox | http://localhost:3000/mailbox |
| Health check | http://localhost:3000/health |

### Bangladesh store defaults (`store:init`)

On every start, the server sets up what a Bangladeshi store needs and is still missing: Bangla and English, all countries with only Bangladesh enabled, a "Bangladesh" zone, a 0% standard tax with prices including tax, the channel in BDT, the staff roles (Owner, Manager, Order staff, Packer, Marketing) and the store settings with policy templates. Each step runs once and is recorded, so a merchant's later changes are never overwritten. The server log shows `Store defaults: …` lines the first time.

To run it without starting the server:

```bash
npm run store:init
```

`npm run store:init -- --force` re-applies everything, including the channel's currency and languages if a merchant changed them. It's for operations staff fixing a store; it never creates duplicates. Later phases add their own defaults (shipping in 07, COD in 08…) with `registerStoreDefaults` in the `bd-core` plugin.

### Working on the merchant admin

`npm run dev` serves the built admin at `/admin`. For live reload while changing it, also run `npm run dev:admin` and open http://localhost:5174/admin/ (it forwards API calls to the server on :3000).

### Working on the storefront

The storefront (`apps/storefront`, Astro) is a separate process that reads the core's Shop API:

```bash
npm run dev:storefront
```

It runs on http://localhost:4321 with live reload and forwards `/img`, `/assets` and `/shop-api` to the core on :3000 (set `CORE_URL` for another port). The store's default language (Store settings) has no prefix; the other language is under `/en/` or `/bn/`. Settings live in `apps/storefront/.env.example`. After a Shop API change in the core, refresh the typed schema with `npm run gql:schema -w @ecommbd/storefront` (the core must be running).

Category and search pages use the core's `bdSearch` query (plugin `bd-search`, phase 13), which reads the index kept by Vendure's DefaultSearchPlugin: products appear once the worker has indexed them. Search is rate-limited per shopper address in the core (`SEARCH_RATE_LIMIT_PER_MINUTE` in `apps/core/.env`, default 600).

Cart and checkout (phase 14) post to the storefront's own routes, which use the shopper's `shop-session` cookie with the core. Set `CSRF_SECRET` in `apps/storefront/.env` (32+ random characters; required in staging and production). Order tracking lookups are limited per address with `TRACKING_RATE_LIMIT_PER_IP` in `apps/core/.env` (default 20 per 10 minutes); the browser tests raise it for their own core.

The page editor and theme screen (phase 15, **Online store → Theme / Home page / Product page**, and **Edit sections** on each page) show the storefront in a frame. In development the admin (:3000) and the storefront (:4321) are different origins: the core points preview links at `STOREFRONT_URL` (default `http://localhost:4321` in dev) and the storefront lets `EDITOR_ORIGIN` (default `http://localhost:3000` in dev) frame its preview pages. Live stores serve both on one site, so neither is needed. Publishing purges the storefront's data cache through the cache Redis, so the live page changes within seconds. Section definitions, themes and starter layouts are in `packages/sections`.

## 5. Production build and start

This is how a store runs on a CloudPanel server:

```bash
npm run build
npm start
```

`npm run build` also builds the storefront; start it with `npm run start:storefront` (port 4321, `SITE_URL` set to the store's address). `vendure build all` builds the Dashboard (~11 s) and compiles the server and worker (~1 s). `vendure start all` starts two processes. On the test machine it was healthy in about 5 s, with the server at ~270 MB and the worker at ~150 MB idle. Architecture.md plans to run the worker inside the server process to save that second process; the spike decides.

**Before a store goes live:**

| Item | Where |
|---|---|
| `APP_ENV=production` (also turns GraphiQL off) | `apps/core/.env` |
| A non-default `SUPERADMIN_PASSWORD` (Vendure refuses to start without one) | `apps/core/.env` |
| `CORS_ORIGINS` set to the store's domains | `apps/core/.env` |
| The store's own `REDIS_KEY_PREFIX` and Redis ACL users | `apps/core/.env` |
| Real asset URL (`assetUrlPrefix`, a placeholder in the template) | `vendure-config.ts` |
| Email: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` and `SMTP_FROM` (without them no email is sent). Dev mode and the `/mailbox` page exist only with `APP_ENV=dev` | `apps/core/.env` |
| SMS: a provider driver once one is chosen (until then `SMS_DRIVER=none` records every SMS as not sent), the approved sender ID in Settings → SMS, and `STOREFRONT_URL` for tracking links | `apps/core/.env`, merchant admin |

## 6. Adding a feature: plugins

Each feature area in [architecture.md](docs/architecture.md) (Decision 1, "What we build as plugins") is one Vendure plugin. Scaffold with Vendure's CLI from `apps/core`:

```bash
cd apps/core
npx vendure add -p BdCheckout
```

The CLI creates `src/plugins/<name>/` and registers the plugin in `vendure-config.ts`. Its output shows the plugin's class name; pass that to `--selected-plugin` when adding parts to the plugin:

```bash
npx vendure add -s PhoneCheckoutService --selected-plugin <PluginClass>
npx vendure add -a <PluginClass> --mutationName setCustomerForOrderByPhone
npx vendure add -e IncompleteOrder --selected-plugin <PluginClass>
npx vendure add -j <PluginClass> --name sync-courier-status --selected-service <ServiceName>
npx vendure add -d <PluginClass>
```

These add a service, an API extension, an entity, a job queue and Dashboard pages respectively. Conventions (from Vendure's `AGENTS.md` in `apps/core`):

- Read environment variables in `vendure-config.ts` and pass them in through `Plugin.init()` options.
- Create job queues in `onModuleInit()` / `onApplicationBootstrap()` and reuse them.
- Pass `RequestContext` to Vendure services and `TransactionalConnection` methods.
- Run `npm run build` after backend changes.

## 7. Database changes (migrations)

`synchronize` stays `false` everywhere. After adding an entity or custom fields, generate a migration, review it, and commit it:

```bash
npm run migrate:generate -- add-incomplete-orders
```

The file lands in `apps/core/src/migrations/`. Pending migrations run when the server starts. To run them by hand: `npm run migrate:run`.

The first migration, `<timestamp>-init.ts`, creates the whole schema and is committed. It was generated with `npm run migrate:generate -- init --from-empty`, which diffs against an empty temporary database.

## 9. Staying on upstream Vendure

**Yes, we can keep taking Vendure's updates, and it's less work than Synapse or LibreChat.** With those, the usual way to customise is to edit their source, so every upstream release is a merge with conflicts. Vendure is built to be extended from outside through plugins, config and strategies. As long as our code stays in plugins, an upgrade is a version bump plus a migration.

**Policy:** take Vendure patch releases (security and bug fixes) within a few days, and minor releases within about two weeks. Watch releases on GitHub (`vendurehq/vendure` → Watch → Custom → Releases).

### Upgrade steps

1. **Read the release notes.** Check the [Vendure releases](https://github.com/vendurehq/vendure/releases) and the CHANGELOG for breaking changes and migration notes.
2. **Bump every `@vendure/*` package to the same version:**

   ```bash
   V=3.9.0
   npm install -w @ecommbd/core --save-exact \
     @vendure/core@$V @vendure/dashboard@$V @vendure/asset-server-plugin@$V \
     @vendure/email-plugin@$V @vendure/graphiql-plugin@$V @vendure/job-queue-plugin@$V
   npm install -w @ecommbd/core --save-exact --save-dev @vendure/cli@$V
   ```

3. **Check:** `npm run doctor`.
4. **Migrate:** `npm run migrate:generate -- vendure-$V`. If Vendure's entities changed, this creates a migration. Review it and commit it.
5. **Build and test:** `npm run build`, then `npm test`, `npm run test:e2e` and `npm run test:browser`, then place an order end to end.
6. **Release:** ship through the release pipeline, test stores first (architecture.md, Central system).

### When a core patch is unavoidable (option 3)

1. Install patch-package once at the root (`npm install -D patch-package`) and add `"postinstall": "patch-package"` to the root `package.json`.
2. Edit the file under `node_modules/@vendure/...` and run `npx patch-package @vendure/core`.
3. Commit the generated `patches/@vendure+core+<version>.patch`.
4. Add a line to `patches/README.md`: why, the upstream issue or PR, and when to remove it.
5. Prepare the same fix in the Vendure fork and send it upstream, so the patch can eventually be deleted.

On every upgrade, patch-package re-applies the patches. If one no longer applies, it fails loudly: redo it against the new version, or delete it if upstream fixed it.

### Last resort: building from our fork (option 4)

If patches ever pile up or a change is too big for a patch, switch to the Synapse/LibreChat model:

1. Keep an `ecommbd` branch in our Vendure fork, starting from the release tag.
2. Build and publish the packages to a private registry (GitHub Packages).
3. Merge each new upstream release tag into that branch, resolving conflicts.

This costs real time on every release, so we avoid it. Because our code lives in plugins, switching later is still possible. Going the other way, back to plain upstream after heavy core edits, is not.

## Troubleshooting

| Problem | Fix |
|---|---|
| `Cannot connect to the Docker daemon` | Start Docker Desktop, then `npm run services:up` |
| `Invalid environment configuration: …` | The listed settings in `apps/core/.env` are missing or wrong. Compare with `apps/core/.env.example` |
| `npm warn allow-scripts … install scripts not yet covered` | Informational in npm 11: the scripts still ran. If a future npm blocks them and `bcrypt` or `re2` fails to load, run `npm approve-scripts bcrypt re2 msgpackr-extract esbuild` |
| Port 3000 already in use | Stop the other process, or set `VENDURE_SERVER_PORT` in `apps/core/.env` |
| `Refusing to start: Default superadmin password is configured` | Expected outside dev: set a real `SUPERADMIN_PASSWORD` |
| `BullMQ: Your redis options maxRetriesPerRequest must be null` | Keep `maxRetriesPerRequest: null` in the BullMQ connection in `vendure-config.ts` |
| Anything else odd | `npm run doctor` |
